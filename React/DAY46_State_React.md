# 📚 오늘 배운 내용 정리 (useState: 리액트의 살아있는 메모리)

### 1. 학습 요약
리액트 컴포넌트가 데이터를 '기억'하고 화면을 '새로 고침'하는 유일한 방법인 `useState`의 메커니즘과 파생 변수 활용법을 완벽히 파헤침.

---

### 2. 배운 개념 정리 (State 심화)
1. **일반 변수 vs State**: 
   - 일반 변수는 함수가 끝날 때 사라지거나, 값이 바뀌어도 화면이 그대로임.
   - 스테이트는 함수가 끝나도 리액트가 따로 보관하며, 값이 바뀌면 "화면 다시 그려!"라고 명령함(리렌더링).
2. **비동기적 업데이트 (Batching)**: 
   - `set`함수를 호출한다고 그 즉시 값이 바뀌는 게 아니라, 리액트가 "음, 바꿀 게 이거구나" 하고 메모해뒀다가 다음 렌더링 때 한꺼번에 적용함.
3. **불변성 유지**: 
   - 스테이트를 직접 수정(`state = 1`)하면 안 되고, 반드시 `set`함수를 통해 '새로운 값'으로 갈아 끼워야 리액트가 변화를 감지함.

---

### 3. 코드리뷰 (State 활용 설계 의도)

```javascript
/* [1. 준비물 챙기기] 
useState는 [현재값, 바꾸는 함수]를 반환함. 
초기값 ""은 입력창이 처음엔 비어있음을 의미.
*/
const [password, setPassword] = useState(""); 

/* [2. 설계 의도: 파생 변수의 활용] 
isMatch를 왜 useState로 안 만들었을까? 
이미 있는 'password'와 'confirmPassword'로 계산이 가능하기 때문임.
이걸 '파생된 상태(Derived State)'라고 부르며, 상태 개수를 줄이는 게 실무자의 실력임.
*/
const isMatch = password === confirmPassword;

/* [3. 일 시키기: 세터 함수의 역할] 
setPassword("123")를 실행하는 순간:
1. 리액트 보관소의 password 값이 "123"으로 예약됨.
2. 리액트가 PasswordCheck 함수를 다시 실행함(리렌더링).
3. 새로운 password 값에 따라 isMatch가 다시 계산되고 화면이 업데이트됨.
*/
```

### 4. 헷갈렸던 점 (Q&A )
* **Q: 왜 `isMatch`는 `const`로 선언했는데 값이 계속 바뀌나요?**
  * **A:** 리액트가 화면을 다시 그릴 때마다 함수를 처음부터 끝까지 **다시 실행**하기 때문임. 실행될 때마다 그 시점의 `password` 값을 가져와서 `isMatch`를 매번 새로 만들기 때문에 가능한 마법임.
* **Q: `useState`를 너무 많이 쓰면 안 좋나요?**
  * **A:** 상태가 많아질수록 리액트가 할 일이 많아져서 성능이 떨어지고 코드가 꼬임. 그래서 오늘처럼 '계산 가능한 값'은 변수로 빼는 습관이 중요함.

### 5. 실무 관점 (AI 서비스 개발)
* **상태 관리의 효율성**: AI 에이전트 개발 시, '채팅 목록', '현재 질문', '답변 로딩 여부' 등을 스테이트로 관리하게 됨. 이때 상태 하나가 바뀔 때마다 화면 전체가 버벅이지 않도록 상태를 잘 쪼개고 관리하는 능력이 취업 시 핵심 역량임.
* **사용자 피드백**: 비밀번호 일치 여부를 실시간 스테이트로 보여주는 것처럼, AI 답변이 올 때 '실시간 스트리밍'으로 글자가 써지는 UI도 오늘 배운 스테이트 업데이트 원리를 그대로 응용함.
