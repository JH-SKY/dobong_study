# SNS 서비스 고도화 설계를 통한 DB 관계 및 실무 설계 이해

### 1. 학습 요약
팔로우, 단체 채팅, 알림 시스템 등 SNS의 핵심 기능을 설계하며 복잡한 다대다(N:M) 관계를 중간 테이블로 풀어내는 실무적인 방법과 명확한 네이밍의 중요성을 학습했다.

### 2. 배운 개념 정리
- **다대다(N:M) 관계와 중간 테이블**: 유저 한 명이 여러 채팅방에 들어갈 수 있고, 채팅방 하나에도 여러 유저가 있을 수 있는 관계다. 이럴 땐 '채팅 참여자'라는 중간 테이블을 만들어 1:N 관계로 쪼개야 데이터 관리가 가능하다.
- **자기 참조(Self-Join) 관계**: 팔로우처럼 '유저가 유저를' 관계 맺는 경우다. 똑같은 유저 데이터지만, '팔로우를 하는 사람'과 '받는 사람'의 역할을 컬럼명으로 명확히 구분해야 한다.
- **알림(Notification)의 확장성**: 다양한 이벤트(좋아요, 댓글, 팔로우)를 하나의 테이블에서 통합 관리하기 위해 '어떤 타입인지', '어디서 발생했는지'를 설계하는 법을 배웠다.

### 3. 코드리뷰
오늘 설계한 ERD 구조 중 가장 핵심이 되는 '채팅 참여자' 테이블의 SQL 예시이다.

```sql
-- [채팅 참여자 중간 테이블 설계]
CREATE TABLE chat_participant (
    participant_id INT PRIMARY KEY AUTO_INCREMENT,
    user_id INT NOT NULL,  -- 채팅방에 들어온 사람
    room_id INT NOT NULL,  -- 참여한 채팅방 번호
    joined_at DATETIME DEFAULT CURRENT_TIMESTAMP, -- 참여 시점
    
    -- 관계 설정: 유저나 채팅방이 삭제될 때의 정책을 정할 수 있음
    FOREIGN KEY (user_id) REFERENCES users(id),
    FOREIGN KEY (room_id) REFERENCES chat_rooms(id)
);
/* 설계 의도: 
단순히 유저 테이블에 채팅방 ID를 넣으면 한 명당 하나의 방만 가질 수 있는 문제가 생긴다.
이렇게 별도의 참여자 테이블을 두면 단체 채팅방도 무한히 확장 가능하다.
*/
```

### 4. 실수/에러와 해결 과정
- **문제점**: 처음에는 팔로우 테이블의 변수명을 `user1`, `user2`처럼 모호하게 설정했다.
- **해결 과정**: 코딩이나 DB 설계에서 가장 중요한 건 '의도'가 드러나는 이름이다. `follower_id`(팬)와 `following_id`(스타)로 이름을 바꾸니 데이터의 방향성이 한눈에 들어왔다. 영어 단어 선택 하나가 시스템의 이해도를 바꾼다는 것을 실감했다.

### 5. 실무 관점의 참견
오늘 배운 중간 테이블 설계는 실무의 기본 중의 기본이다. 특히 단체 채팅의 경우, 단순히 누가 참여했는지를 넘어 '이 사람이 메시지를 어디까지 읽었는지(Last Read ID)' 같은 정보도 이 참여자 테이블에 담게 된다. 나중에 서비스가 커지면 알림 테이블은 엄청나게 무거워지므로, 인덱스(Index) 설계를 아주 신중하게 해서 조회 속도가 느려지지 않게 관리하는 것이 시니어 개발자의 핵심 역량이다.
